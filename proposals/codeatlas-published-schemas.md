Status: Accepted program child; Phase 1 complete, Phase 2 next

Decision scope: Generated JSON Schemas for every public versioned CodeAtlas
JSON artifact, a drift-tested schema registry, and CodeAtlas-owned annotation
keys at external contract boundaries

Depends on:

Unblocks:

## Decision

CodeAtlas will check in deterministic Draft 2020-12 JSON Schemas under
`schemas/` for every public, versioned JSON report or artifact. The schema is
generated from the owning Rust model, not maintained as a hand-written second
model. A registry test regenerates all schemas in memory and byte-compares them
with the committed files.

This proposal does not change existing report payloads merely to make their
version fields look uniform. Existing integer `schemaVersion`/`schema_version`
and separate `apiVersion`/`api_version` fields remain exactly as shipped until
an owning product change requires a new schema version. New execution artifacts
start with one namespaced string such as `codeatlas.execution-plan/v1`; they do
not copy the older integer-plus-API split.

External schemas remain externally owned. In particular, CodeAtlas will bind
to the current published source-target contract only after its superseding
core-plus-annotations schema is available. CodeAtlas will not preserve or
republish the obsolete draft that placed every producer-specific coordinate in
the core block.

## Why this is one owner

Today a consumer can read CodeAtlas JSON but cannot validate it without
reimplementing private Rust types. Hand-authored schemas beside those types
would only move that duplication into this repository. The accepted shape is:

```text
domain Rust model
       |
       v
schema derivation
       |
       v
published_schemas registry -> schemas/*.schema.json
       |
       v
drift test compares exact generated bytes
```

Domain modules continue to own field meaning and versions. The registry owns
only root registration, stable contract IDs, filenames, canonical schema
serialization, and drift enforcement. `src/outputs` does not own schemas
because rendering cannot redefine a report contract.

## Published surface

The initial inventory includes every JSON root emitted by a stable public
command:

- Code scan, code check/usage, and public API baseline artifacts.
- Exact code inspection/context slices.
- Lexicon code reports.
- Test inventory, impact, and witness reports as distinct roots.
- HTTP inventory, check, baseline, diff, and fuzz reports as distinct roots.
- PostgreSQL inventory, check, test, baseline, and diff reports as distinct
  roots.
- Architecture compilation/lock, observation, conformance,
  source-conformance, provider-query inspection, and diagnostic reports.

An internal cache entry, request-adapter message, temporary engine event, or
private transport envelope is not promoted to a public schema merely because
it contains a version field. If another tool must consume one, the owning
proposal must first make it an explicit public artifact.

Each registry entry records:

```text
contract ID       codeatlas.http-inventory/v2
root Rust type    HttpInventoryReport
schema path       schemas/codeatlas-http-inventory-v2.schema.json
payload version   existing fields and constants, unchanged
owner             http
```

Where several roots currently share one `apiVersion`, the published contract
ID remains root-specific. That registry identity does not add or alter a field
inside the existing payload.

## Generation and drift contract

- Root and nested types derive schema evidence from the same serde attributes
  that control serialization.
- `deny_unknown_fields`, field renames, defaults, enum spellings, required
  fields, and integer bounds remain visible in generated output where the
  runtime contract enforces them.
- Generated objects and definitions use deterministic ordering and a final LF.
- Absolute paths, build paths, timestamps, toolchain paths, and hash-map order
  never enter a schema.
- One explicit developer update task rewrites all registered schema files; the
  normal test path is read-only and fails with the exact stale filenames.
- Removing or renaming a registered root requires an owning version decision;
  the generator never silently deletes a schema.
- A serialized field change and its schema update land in the same commit.
- Every new public JSON artifact must register before its implementation phase
  can complete.

Schema generation is development-only. CodeAtlas does not add a public
`schemas` CLI command or turn the binary crate into a library solely to expose
private models. The registry and generator compile only in tests; the owning
models carry direct compile-time `JsonSchema` evidence so ordinary source
analysis does not misclassify 198 conditional derives as dynamic boundaries.
`JsonSchema` is explicitly reachability-inert, and the source-index algorithm
identity is bumped so cached evidence cannot preserve the older classification.

## New-artifact version rule

New plan, receipt, observation, baseline, reproducer, report, and interop
artifacts use one namespaced schema-version string. The owning artifact proposal
defines the exact value and fields; this registry rejects:

- an unqualified integer as the only new artifact identity;
- a second parallel API-version field with the same purpose;
- a version string reused for two incompatible root shapes;
- a schema bump without a corresponding generated schema;
- a payload change under an unchanged namespaced version.

This rule is prospective. Existing reports are not churned and consumers do
not receive compatibility aliases.

## Source-target annotations

The superseding external source-target contract owns its core fields and an
`annotations` map. CodeAtlas owns only keys in the `codeatlas.` namespace.
Registered keys use `codeatlas.<lower_snake_case_name>`; they may not shadow a
core field, change the meaning of another producer's key, or carry a value
whose shape is not documented and drift-tested.

The first reserved key is `codeatlas.node_id`, whose value is an opaque exact
CodeAtlas graph node ID. If the accepted external contract places symbol
identity outside its core, CodeAtlas will additionally register
`codeatlas.symbol`; that is one serialization choice, not a new target model.
Unknown future `codeatlas.*` keys are not emitted until registered. CodeAtlas
fills only coordinates it truthfully knows and never fabricates a UTF-16 range
from a line or asks another tool to parse a CodeAtlas symbol selector.

The external core-plus-annotations schema remains the sole contract owner.
CodeAtlas tests bind its serializer to that published schema when available;
this repository does not check in a competing source-target draft.

## TypeMill interoperability wording

This proposal records a dependency boundary, not a TypeMill implementation.

- A TypeMill plan write set may feed `usage tests --changed` only when both
  artifacts explicitly use the same repository root. CodeAtlas does not guess
  or auto-detect a cross-tool root.
- Any future TypeMill receipt verification performed by CodeAtlas must be
  **closed over the exact plan plus receipt alone**: plan identity, receipt
  linkage, operation results, and published digests must be verifiable without
  consulting mutable ambient workspace state.
- A resulting digest for a moved path is pending TypeMill's publication audit.
  CodeAtlas does not assume that field exists and does not advertise moved-path
  verification until the published receipt schema proves it.
- Findings-to-preview integration waits for the accepted external source-target
  schema and an advertised TypeMill capability. CodeAtlas carries truthful
  coordinates and fabricates neither ranges nor symbol handles.

No CodeAtlas phase edits TypeMill, HQA, or a neutral contracts repository.

## Existing-first check

Reuse:

- Serde models and version constants in each current domain owner.
- Existing strict architecture schema/canonicalization tests as evidence for
  deterministic generation, without treating their hand-authored DSL schema as
  the owner of report schemas.
- Existing exact JSON fixtures and CLI acceptance tests as behavior that the
  generated schemas must accept.

New owners are limited to a small schema registry, committed `schemas/`
artifacts, and focused drift tests. There is no second report model, schema
service, runtime network dependency, or public schema-generation command.

## Acceptance gates

- Every public versioned JSON root in the inventory has exactly one registry
  entry and one committed schema.
- Every committed CodeAtlas report fixture validates against its registered
  schema.
- Generated bytes match the checkout exactly on a clean run.
- A serde rename/default/enum/required-field test mutation makes the drift test
  fail before a schema is regenerated.
- New execution artifacts use one namespaced string; existing report payloads
  remain byte-compatible.
- The `codeatlas.` annotation namespace and each emitted key have one documented
  owner and value shape.
- No obsolete source-target block or guessed moved-path receipt field is
  checked in.
- Schema generation writes no build or temporary state under `/workspace`.

## Layman's wins

- Other tools can validate CodeAtlas output instead of reverse-engineering it.
- Schema files cannot quietly drift away from the Rust that writes the JSON.
- New artifacts start with one clean version identity while old consumers are
  not churned.
- Cross-tool target and receipt claims stay explicit about what CodeAtlas can
  actually verify.
